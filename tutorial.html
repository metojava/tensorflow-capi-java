TensorFlow C API from Java — build & run guide

This Maven project wraps the TensorFlow C API in a small Java library via JNI, and ships a demo application that classifies Fashion-MNIST images with a model trained in Python/Keras. Everything native is compiled with gcc (MSYS2/UCRT64); no official TensorFlow Java binding is used.

Architecture

FashionMnistDemo.java          your application
        │  calls
TfModel.java / TensorFlow.java  thin Java wrapper (native methods)
        │  JNI
tf_capi_jni.c                   C bridge, compiled by gcc into tf_capi_jni.dll
        │  links against
tensorflow.dll                  official TensorFlow C library (2.18.x)

The bridge loads a Keras-exported SavedModel (produced by ..\classification.py), feeds float tensors in, and copies probability tensors back to Java as float[].

All machine-specific paths live in two places only: the <tf.capi.home> and <msys2.bash> properties at the top of pom.xml, and the default path inside src/main/java/com/example/tfcapi/TensorFlow.java (overridable via the TF_CAPI_DLL environment variable).

Step 1 — Build the native JNI DLL

All gcc logic lives in one shell script, src/main/native/build-native.sh. It:

  1. locates itself (dirname $0) so it works from any working directory;
  2. converts JAVA_HOME to a POSIX path with cygpath;
  3. compiles tf_capi_jni.c with -D_JNI_IMPLEMENTATION_ (makes MinGW export the JNI functions);
  4. links directly against tensorflow.dll (GNU ld generates import stubs itself, so the MSVC-format tensorflow.lib is not needed);
  5. writes target\native\tf_capi_jni.dll using an absolute path and verifies the file exists afterwards.

Run it standalone:

build.cmd

or let Maven do it automatically — the pom's maven-antrun-plugin invokes the same script during the generate-resources phase of every build.

Why a script file? Injecting the gcc command line directly into pom.xml breaks reliably: when a JVM spawns bash.exe, the MSYS2 runtime rewrites arguments that look like paths — quoted strings get their quotes stripped and backslashes are eaten. Passing the script filename plus simple space-free arguments survives that boundary untouched.

Step 2 — Build the Java side

mvn clean package

This runs the native step above, compiles the three Java classes, and produces target/tensorflow-capi-java-1.0.0.jar.

Step 3 — Run the demo application

mvn compile exec:java

No PATH fiddling needed: TensorFlow.load() pre-loads tensorflow.dll by absolute path before loading the JNI DLL, so Windows resolves the dependency from the already-loaded module.

Optional arguments (defaults shown):

mvn compile exec:java ^
  -Dexec.args="../classification/fashion_model ../data/fashion/t10k-images-idx3-ubyte.gz ../data/fashion/t10k-labels-idx1-ubyte.gz 10000"

Using the wrapper in your own code

import com.example.tfcapi.TensorFlow;
import com.example.tfcapi.TfModel;

public class MyApp {
    public static void main(String[] args) {
        System.out.println(TensorFlow.version());      // loads natives on first use

        try (TfModel model = new TfModel("fashion_model")) {
            float[] pixels = /* 28*28 floats normalized to [0,1] */;
            float[] probs = model.run(pixels, new long[]{1, 28, 28});
            long[] shape = model.outputShape();         // e.g. [1, 10]

            int best = 0;
            for (int i = 1; i < shape[1]; i++)
                if (probs[i] > probs[best]) best = i;
            System.out.println("Predicted class " + best);
        }
    }
}
  • run() takes one batch per call; inShape product must equal input.length.
  • Returns the flattened output tensor; its dimensions are available via outputShape().
  • TfModel is AutoCloseable; closing releases the native session. Instances are synchronized and must not be shared across threads while running.

Troubleshooting

SymptomCause and fix
UnsatisfiedLinkError: no tf_capi_jni in java.library.path The JNI DLL was not built or is not at target\native\tf_capi_jni.dll. Run build.cmd or mvn package.
UnsatisfiedLinkError naming a method like TensorFlow.version() Natives never loaded. Call TensorFlow.load() first (the wrapper methods do this automatically).
Can't find dependent libraries when loading tf_capi_jni.dll tensorflow.dll was not pre-loaded and is not on PATH. Set TF_CAPI_DLL to its full path, or add its folder to PATH.
DLL disappears right after building / exe works then stops Antivirus real-time protection quarantined the unsigned DLL. Add the project folder to the Defender exclusions.
cc1.exe: fatal error: tf_capi_jni.c: No such file or directory The script was moved or invoked from another location without its self-locating cd "$(dirname "$0")" logic.
NATIVE_BUILD_OK but DLL is somewhere unexpected Relative output paths (../../x) resolve differently depending on who spawned bash. The script derives everything from its own location — keep it that way.
JAVA_HOME is not set Set it to the JDK root (gcc needs %JAVA_HOME%\include\jni.h).
gcc exits silently with code 1 when run straight from PowerShell/cmd Known environment quirk: gcc's internal cc1.exe child fails to start outside an MSYS2 shell. Always go through build-native.sh/build.cmd or the MSYS2 UCRT64 shell.
Error loading model ... Export directory does not contain a SavedModel Run python ..\..\classification.py first, and pass the correct model dir as the first demo argument.

Training a model from scratch in Java

Besides running exported SavedModels, the wrapper can build and train a small neural network natively — no Python anywhere:

try (SimpleNeuralNet net = new SimpleNeuralNet(784, 128, 10, 0.15f)) {
    for (int epoch = 0; epoch < 8; epoch++) {
        for (each batch) {
            float loss = net.trainBatch(batchX, batchY);   // one SGD step
        }
    }
    float[] probs = net.predict(testBatch);                // rows of 10 probabilities
}

Internally the C bridge constructs the graph (Relu(x·W1+b1) → logits → LogSoftmax CE), differentiates it with TF_AddGradients, and applies SGD updates on native parameter tensors. A consumer project that trains Fashion-MNIST this way lives in C:\Users\dell\Desktop\fashion-mnist-java, which uses this wrapper as a plain Maven dependency (com.example:tensorflow-capi-java:1.1.0; run with mvn compile exec:java). It reaches ~86% test accuracy in ~10 s on CPU.

Note: the cross-entropy is composed from primitives (LogSoftmax, Mul, Sum, Neg, Mean) because SparseSoftmaxCrossEntropyWithLogits has no gradient registered in the C++ gradient registry that TF_AddGradients relies on — its gradient exists only in Python.
Tested with: TensorFlow C library 2.18.1 (CPU, windows-x86_64), JDK 17 (Oracle), Maven 3.9.9, MSYS2 gcc 16.1.0 (ucrt64), Windows 11 x86_64.
